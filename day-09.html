用户说“先停一下”，
旧回答 400 ms 后才回来。

数字人当场安静了，用户很满意。半秒后，一个不是这一轮的声音又响起来——因为“让扬声器停下来”和“让这次回答作废”是两件完全不同的事。今天只解决这一件事：把“取消”从声学层抬到状态层。

先画出六节点链 ↓
贯穿今天的一个问题

用户打断正在说话的数字人，旧 LLM 回答在新回答之后才返回。只暂停扬声器，足够吗？

不够。暂停扬声器只是把已经到达音频设备的样本停掉。它拦不住三样东西：LLM 流里还没吐完的 token、TTS 已经合成好但不一定已经送进设备的音频块、以及这些产物在下一个话轮里被重新送进播放队列。真正的答案是一个版本条件：旧版本产生的任何结果，一律丢弃。

今天要分清的四件事

14plan 反复要求把材料分成四类，这一页每一块都按这个纪律标：概念解释（原理说得通）、纸面设计（我设计了但没实现）、实际运行（我跑过并有日志）、历史成果（过去项目里真实发生过的）。

本页所有内容属于概念解释 + 纸面设计。我没有运行任何 ASR / TTS / LLM 推理服务，也没有任何陪伴机器人的实机部署记录。这句话不是免责声明，是这一页的可信度来源——把边界说死，剩下的部分才站得住。

为什么“打断”比“不打断”难这么多？

不打断的系统是单向流水线：说完 → 识别 → 生成 → 播放，每一步只依赖上一步，天然串行。一旦允许打断，整条链变成并发的、可撤销的：用户的新输入要和正在生成的旧回答竞争，而旧回答的每一段产物可能在任何时刻、在任意一层（token 流、TTS 合成队列、音频设备缓冲）里冒出来。并发 + 撤销 = 需要版本号。这是本页唯一的核心结论。

延迟预算：用户等到第几毫秒开始不耐烦

首响延迟（用户说完到听见第一个音节）由四段累加。调一调，看总时长和“用户耐心线”的关系——超过 1.5 s，人会怀疑设备没听到，开始重复或者放弃。

四段里最值钱的是 VAD：把端点判定从 300 ms 降到 150 ms，用户感知到的“反应快”提升，比把 LLM 换快一倍更明显——因为那是每句话都要付的固定成本。

一个反直觉的点：缩短首响延迟和“可打断”是两件不同的事。延迟再低，旧回答也会在新回答之后到达——因为你不能假设网络的返回顺序等于你的发起顺序。

写法看起来像什么症状

三条竞态里最阴的是第 ③ 条：它不产生任何报错，只是让用户听见一句不该出现的话。没有断言就永远发现不了。

为什么“第二次插话”比第一次更难

第一次打断时，epoch 从 1 变 2，T1 的产物全部失效，判据干净。第二次打断发生在 CANCELING 还没结束时——此时 T2 自己也已经产生了半句内容，用户又把它打断了。如果你用“当前 turn_id”判断，T2 和 T3 的产物会混在一起；只有单调递增的 generation_epoch 才能区分“T2 被打断前”和“T3 开始后”。

T1 的残块到达1（旧）T2T1丢弃

过期结果过滤：
四个闸门，全过才播。

这是本页最该背下来的一段。一个到达的音频块要被播出去，必须同时通过四道判断；任何一道不过，直接丢弃。把四个条件随便关掉一个，看会发生什么。

过期过滤判定器关掉一个闸门看后果
判定接受并播放
失效的闸门无

四个闸门对应四个不同的失效原因：① 串会话、② 串话轮、③ 版本过期、④ 队列已清空但块还在飞。任何单独一个都拦不住全部四种——这就是为什么“只暂停扬声器”必然漏。

“只暂停扬声器”到底拦住了什么

层暂停扬声器能拦住吗为什么
音频设备缓冲区里已写入的样本能（部分）这是唯一“物理可停”的一层
TTS 已合成、还在播放队列里排队的块不一定取决于播放器是否支持 flush；有的实现只是停止出流，队列还在
TTS 合成器正在生成、尚未交付的块不能合成任务已经发出，取消需要单独的信令
LLM 流里还没吐完的 token不能它根本不知道扬声器停了，会继续生成到结束
下一轮到达的“旧版本”产物不能没有任何状态记住“这一轮已经作废”
一句话版本：暂停扬声器是让声音停下来；丢弃旧 epoch 是让这次回答作废。前者是声学动作，后者是状态动作。用户要的是后者，而大多数人只做了前者。
06 对应 14plan Day 9 · 第 4 阶段

陪伴机器人：
“聊天”和“异常确认”是两条业务流。

它们共用同一个麦克风和同一个扬声器，但风险等级、失败代价、退出条件完全不同。把它们做成一条流程，是这类系统最常见的架构错误。

维度聊天流异常确认流
目标让对话自然、可打断、有来有回确认是否存在需要人介入的情况
答错的代价用户重复一遍 / 觉得笨漏报风险，或误报造成恐慌与打扰
允许 LLM 自由发挥吗可以不可以：LLM 不做独立医疗诊断
打断语义立即停止，丢弃旧版本可以停止说话，但不能停止流程（确认状态必须保留）
退出条件用户不说话了就结束必须有明确结论：已确认安全 / 已转人工 / 用户明确拒绝 / 超时升级

一次异常值的处理链

14plan 给的顺序是：检查信号质量 → 连续性 / 置信度 → 询问是否需要帮助 → 在用户授权规则内转人工 / 家属。注意第二步在第三步前面：先判断这个值可不可信，再决定要不要打扰用户。顺序反了，就会因为一次传感器抖动半夜给家属打电话。

报警分级与三条退出路径点分级看处置
路径正确处置禁止动作
误报（信号质量差 / 单次异常值）记录 + 降级 + 提高后续判定阈值 + 不打扰用户直接按最高级报警；向用户宣称“检测到异常”
用户明确拒绝帮助记录拒绝事实与时间，尊重决定，告知可随时改变，只在授权规则内保留后续升级权反复劝说、绕过用户直接通知家属
网络断连本地兜底：给出“我暂时联系不上，请按预设方式联系 X”，并记录断连时长假装已经通知成功；静默失败

分级的意义不是“严重程度排序”，而是决定谁被打扰：L0 不打扰任何人，L1 只打扰用户，L2 打扰家属，L3 打扰专业人员。每一级都必须是用户事先同意的。

一条不能含糊的边界：“情感交互”里的表达（语气、表情、共情措辞）可以由 LLM 生成；判断（是否存在危险、是否需要升级）不能由 LLM 独立下结论，只能由规则 + 传感器置信度 + 人工授权共同决定。

不够。暂停扬声器只停止已经写入音频设备的样本，它不改变系统的状态。旧 LLM 流仍然会继续产出 token，TTS 合成任务仍然会继续交付音频块，而这些块到达播放器时，播放器没有任何依据判断它们属于“已经作废的那一轮”。

最小实现是给每一轮分配单调递增的 generation_epoch，并让所有下游产物携带它出生时的 epoch。播放前过四个闸门：session 相同、turn 相同、epoch 等于当前、队列版本未被 flush。任一不过就丢弃——不入队、不缓存。打断时 CANCELING 状态要持续到“旧 epoch 产物全部确认丢弃”才退出，而不是在发出取消信令时退出。

证据方面：我用事件日志跑了五条断言（同 chunk 不重复 play、T1 的 play 全早于 cancel、无旧 epoch 进入设备、cancel 后 300 ms 静音、T2 首播晚于 T1 取消）。这套断言我目前只在纸面上设计，还没有实际运行——所以我现在能说的是“设计成立”，不能说“实测通过”。

    范围来自 Day 9 任务手册：R09（aha-voice 语音流水线源码与状态管理结构）、R10，以及任务手册「实际任务补强」四节（六状态、t0–t4 时序、异常分支、报名与模拟）。

    本页做了什么、没做什么

    本页提供可执行的设计纪律：六节点链的节点合同、六状态迁移的合法性、t0–t4 每一步的责任归属、四条过期过滤闸门、五条无双重播放断言、报警分级与三条退出路径。

    本页没有运行任何 ASR / TTS / LLM 推理服务，没有接入任何真实语音设备，没有任何实机延迟数据，也没有陪伴机器人的现场部署记录。页面上出现的毫秒数都是用于理解量级的示意值，不是实测值——真值取决于你的硬件、模型和网络。

    六状态机是学习用草案，不是 INZ Lab 或任何产品的内部实现。关于 INZ Lab 的部分只使用可披露的高层描述（多模态情感交互的研究方向），不包含企业内部实现、未公开数据或内部文档。任何“我在这个系统里做了什么”的说法，都必须按四格表（本人做过 / 团队成果 / 开源现有功能 / 拟研究）逐条标注后才能写进材料。
