## 01 · 同一扇门，有四种不同的问题。

*在看公式之前，先看信息*

[本节网页与交互](../day-03.html#world-layers)

想象你在 UE 中摆出两个房间和一扇门。画面已经能看见门，但“看见”没有说明它是否连通、是否够宽、是否打开，以及角色是否会操作它。这些信息需要分别表示。

**动手看**

依次切换四层信息。场景没有变，留意每层回答的问题怎样变了。然后切换“窄门”或“缺技能”，看看哪一层首先出现问题。

**交互入口：[同一场景的四层信息](../day-03.html#day3-layers)**

*图示说明：同一教学场景的不同描述。连通图的边表示声明的连接；它本身没有承诺门处于打开状态，也没有承诺机器人可以通过。*

**把检查问题放回合适的位置**

| 信息 | 今天的例子 | 它还没有回答什么 |
| --- | --- | --- |
| 拓扑 | A 与 B 由门 D 相连 | 门有多宽、是否锁着 |
| 几何 | 门净宽、机器人尺寸、门把高度 | 现在是否有钥匙、是否已开门 |
| 当前状态 | 机器人在 A，门锁着，杯子在 B | 机器人具备哪些操作能力 |
| 动作能力 | 会移动、解锁、开门、抓取 | 这一次具体姿态和轨迹是否可行 |

这些层会一起工作。把门加宽可以改变通行几何；给机器人一把钥匙可以改变库存状态；增加解锁动作可以改变可用能力。你需要明确改的是哪一项，才能解释为什么结果变了。

## 02 · 状态，就是“此刻哪些事实成立”。

*Object · Predicate · State · Goal*

[本节网页与交互](../day-03.html#states)

先把关注的东西命名：机器人 `r`、房间 `a / b`、门 `d`、钥匙 `k`、杯子 `cup`。这些名字指向**对象**。类型告诉程序哪些东西是机器人、房间、门、钥匙或可拿取物。

**谓词 predicate** 是一句可以判断真假的描述模板。例如“谁在什么房间”写成 `at(谁, 房间)`。填上具体对象，`at(r, a)` 就是“机器人 r 在房间 a”这个可以核对真假的命题。

| 表达方式 | 内容 |
| --- | --- |
| 中文句子 | **机器人在 A 房间** |
| 说明式记法 | `at(r, a)` |
| PDDL 写法 | `(at r a)` |

这两种符号写法在这里指同一件事。PDDL 用括号和空格表达关系，**不是在调用 Python 函数，也不是让机器人移动**。它只是在描述一个事实。

**动手看**

从初态切到“解锁后”，找出被删掉和新增的事实。再切到“开门后”：门已经解锁时，为什么还需要这一步？

**交互入口：[世界状态与真假事实](../day-03.html#day3-state)**

*图示说明：几张有效状态快照共享同一场景。它们展示的是符号模型中的事实；真实系统还需要传感与状态估计，把观测转换成这样的表示。*

### 不把“门没锁”和“门已打开”合成一个词

`locked(d)` 表示锁着，`unlocked(d)` 表示已经解除锁定，`opened(d)` 表示门已经打开。门解锁以后仍可以关着。今天的动作规则会维护锁定与解锁互斥，并让 opened 只在解锁后产生。

这些一致性**不是 PDDL 自动理解了常识**：是我们正确设置初态，并写对动作的增加与删除效果。若初态同时写“在 A”和“在 B”，规划器不会替你理解“一个机器人不能分身”。

### 初态写现在；目标写想要的结果

**初态 initial state** 是起点的事实集合。**目标 goal** 是结束时必须成立的要求。本例目标只有 `(holding r cup)`：杯子在机器人手中。它没有要求“最后关门”，也没有要求“返回 A”；如果任务确实要求这些，需要继续写进目标或其他合适的约束。

**目标不是动作清单**

“杯子在手里”描述结果；“解锁 → 开门 → 移动 → 抓取”是一条候选办法。规划要做的，是根据初态与动作规则找到办法。

<details>
<summary>为什么没有写出来的事实，在这个模型中当作假？</summary>

本页使用完全已知、确定性的经典规划模型，只列当前为真的事实；其他已定义的具体命题按闭世界假设视为假。例如初态没写 `(opened d)`，模型就把门当作未打开。这是模型约定。

真实相机没看见门把手，可能只是被遮挡；“没有观测到”不能直接变成“现实中不存在”。若机器人不知道门是否锁着，需要表示知识或不确定性，并考虑观察动作，已经超出本页的完全已知模型。

</details>

<details>
<summary>有钥匙为什么又可以“手空”？</summary>

这里的 `has-key` 表示钥匙在机器人的物品栏，可用于解锁，不占用拿杯子的那只手；`handempty` 只表示抓杯子的手空着。这是教学假设。若现实中必须同一只手拿钥匙、插锁、收起钥匙再抓杯，就需要为这些过程增加对象状态和动作。

</details>

<details>
<summary>先自己说：把目标改成“杯子放在桌上”，只改一句中文够吗？</summary>

还要把桌子和目标关系表示出来，例如 on(cup,table)，并提供能产生它的放置动作及前置条件。目标描述得出来，不代表当前动作集合一定能到达它。

</details>

基本语义依据 [Helmert《An Introduction to PDDL》](../day-03.html#source-pddl)；门、钥匙与手的具体约定由本教程明确给出。

## 03 · 一个动作，要同时写清“能否做”和“做完变什么”。

*Precondition · Add Effect · Delete Effect*

[本节网页与交互](../day-03.html#actions)

以进入 B 房间为例。至少要先在 A，有一条连接 A 与 B 的门，门已经打开，而且机器人有移动能力。这些“做之前必须为真”的条件叫**前置条件 precondition**。

符号动作成功应用后，机器人变成在 B，并且不再在 A。这些变化叫**效果 effect**。今天采用的 STRIPS 形式把效果分成：增加为真的事实，以及删除、不再为真的事实；没有涉及的其他事实保持不变。

**状态更新公式**

> 新状态 =（旧状态 − 删除的事实）∪ 新增的事实

你可以先把它理解成编辑一个事实集合：划掉旧位置，补上新位置。公式中的“减”和“并”是集合操作，不是在算房间坐标。

**动手看**

在初态先尝试 move，读每一项前置为什么通过或失败。再按 unlock → open → move → pickup 操作，逐步观察“新增、删除、保持不变”。

**交互入口：[检查前置并逐步应用动作](../day-03.html#day3-actions)**

*图示说明：只有前置全部成立，符号状态才迁移。这里的按钮应用确定性动作模型；它没有向真实机器人发送命令。*

**四种动作的中文合同；完整谓词与参数见可运行 PDDL**

| 动作 | 做之前需要 | 新增 | 删除 |
| --- | --- | --- | --- |
| unlock 解锁 | 在门的一侧，持有匹配钥匙，有解锁能力，门锁着 | 门已解锁 | 门锁着 |
| open 开门 | 在门的一侧，门已解锁，有开门能力 | 门已打开 | 无 |
| move 移动 | 在起点，声明的连接存在，门打开，有移动能力 | 在终点 | 在起点 |
| pickup 抓取 | 与杯同房，杯被声明可抓，手空，有抓取能力 | 持有杯子 | 杯仍放在原房间、手空 |

**每条条件都要问它从哪里来。**“与杯同房”是粗粒度关系，不等于机械臂能碰到杯子；`graspable(cup)` 是本例给定的物体属性，也没有证明某个具体抓取姿态无碰撞。第 7 节会把这些连续空间问题接回来。

<details>
<summary>open 的删除效果为空，是不是忘写“关门”？</summary>

本例没有单独的 closed 谓词，门未打开由 opened 不在事实集合中表示。open 加入 opened 即可。若模型同时使用 closed，就需要正确删除 closed，并维持两者一致。表示方法可以不同，前提是语义一致。

</details>

<details>
<summary>模型写了效果，现实就一定发生了吗？</summary>

规划时，效果描述“按这个动作模型成功后，预期状态怎样变化”。执行时，电机卡住、抓取滑落或观测错误都可能使预期落空。真实系统需要检测动作结果，用最新观测更新状态，再决定是否继续或重规划。

</details>

<details>
<summary>先自己说：move 只增加 at(r,b)，忘删 at(r,a)，会怎样？</summary>

机器人会同时出现在两个房间的符号事实中。后续动作可能利用这个错误产生虚假的可行计划。问题在模型的效果定义，不能靠规划器“常识理解”补救。

</details>

正负效果与未涉及事实保持不变，见 [PDDL 入门原讲义](../day-03.html#source-pddl)；动作合同对应 [Day 3 的门杯练习](../day-03.html#source-plan)。

## 04 · 把刚才的中文，写进两份文件。

*Domain 是规则，Problem 是这一次的题目*

[本节网页与交互](../day-03.html#pddl)

**PDDL** 全称 Planning Domain Definition Language，是一种描述规划问题的语言。它负责把对象、状态和动作规则写清楚。**规划器 planner** 才是读取描述并搜索计划的程序；“写了 PDDL”与“已经求出计划”是两件事。

可以把 **domain** 理解成这一类任务的规则说明：有哪些类型、哪些关系、哪些动作。把 **problem** 理解成当前这一题：有哪些具体对象、起点是什么、最终要什么。换一个初态，通常可以继续使用同一套动作域。

**动手看**

在右侧切换“钥匙缺失”和“已经开门”。观察哪份文件发生了变化，再解释为什么开门动作的定义不用跟着改。

**交互入口：[对照 Domain 与 Problem](../day-03.html#day3-domain)**

*图示说明：对照中文含义与 PDDL 片段。浏览器演示限定于本页的门杯模型；配套文件由实际 PDDL 解析器读取并运行。*

**第一次读文件，先找到这七个标记**

| 位置 | 标记 | 你可以问自己 |
| --- | --- | --- |
| domain | `:types` | 世界里有哪几类对象？ |
| domain | `:predicates` | 程序可以描述哪些关系？ |
| domain | `:action` | 允许怎样改变状态？ |
| action | `:parameters / :precondition / :effect` | 作用于谁？何时能做？做完变什么？ |
| problem | `:objects` | 这一次具体有谁？ |
| problem | `:init` | 现在什么是真的？ |
| problem | `:goal` | 结束时哪些要求必须成立？ |

### 把一个动作逐行翻译回来

```lisp
(:action move
  :parameters (?r - robot ?from ?to - room ?d - door)
  :precondition (and
    (at ?r ?from)
    (connected ?from ?to ?d)
    (opened ?d)
    (can-move ?r))
  :effect (and
    (at ?r ?to)
    (not (at ?r ?from))))
```

`?r` 是待填入的机器人参数，`?from / ?to` 是起点和终点参数。把它们分别填成 r、a、b、d，就得到具体动作 `(move r a b d)`。这一步叫**实例化／grounding**，即把“谁从哪里去哪里”的模板变成这一次的动作。

`:effect` 里的 `(not (at ?r ?from))` 表示删除旧事实。它没有说“再去执行一次移动”，也没有让房间消失。代码里的连接关系是声明的符号连接；本例没有把门净宽、姿态与整条运动路径直接写进这个 move 前置。

<details>
<summary>为什么只教这部分 PDDL，不一开始就放全部语法？</summary>

这里使用带类型的 STRIPS 子集：正前置条件、增加／删除效果、有限对象、确定性瞬时动作、完全已知初态。不同规划器支持的 PDDL 扩展不同。时长、代价、数值量、条件效果或不确定性，需要相应语言与求解方法支持；先把最小例子的语义学准，再逐项扩展。

</details>

<details>
<summary>先自己说：增加一间 C 房间，与增加“拿钥匙”动作，分别主要改哪里？</summary>

新增具体房间和连接，主要修改 problem 的对象与初态；新增一种状态改变方式，需要修改 domain 的动作规则，必要时补谓词。当前域没有拿钥匙动作，因此不能假设搜索会自动发明它。

</details>

## 05 · 计划不是猜出来的：从合法动作一步步展开。

*从当前状态，寻找能到达目标的动作序列*

[本节网页与交互](../day-03.html#search)

你刚才已经手工做了规划器最核心的三件事：读当前事实，检查动作前置，计算后继状态。接下来让程序把这些步骤组织起来，查找能满足目标的路线。

1. **从初态开始。**

   先问目标是否已经成立；若成立，空计划就够了。

2. **列出可用动作。**

   前置不成立的动作不能当作合法后继。

3. **应用动作，得到新状态。**

   保留它来自哪个状态、用了哪个动作。

4. **继续展开。**

   找到目标后沿来路还原计划；已经看过的同一状态不必反复展开。

**动手看**

选择标准初态，逐次展开搜索。看到 move 还不可用时，找出缺少的事实。再切到“没有钥匙”，观察搜索如何结束。

**交互入口：[观察有限状态的广度优先搜索](../day-03.html#day3-search)**

*图示说明：浏览器实际执行这个有限门杯域的广度优先搜索。它按状态而不是按屏幕位置去重；Python 实验另用 Pyperplan 读取 PDDL 并搜索。*

### 广度优先搜索 BFS，在这里是什么意思？

先检查能用 0 步达到的状态，再检查 1 步、2 步……待展开状态放在一个**先进先出队列**里。每次从队头取一个，把新的后继放到队尾。这个例子有限、每个动作成本相同，因此找到的第一条计划具有最少动作步数。

“步数最少”没有自动等于路程最短、耗时最少或能耗最低。一次 move 可能实际要走很远，一次 pickup 可能要反复调整手。若你关心这些成本，要改变模型、目标和相应搜索方法。

### 为什么不能把“这个动作失败”当成“整个任务无解”？

初态直接 move 不合法，但先解锁、开门以后就可能合法。拒绝一个动作，只排除了这个时刻的这个选择。本例 BFS 会继续检查其他可达状态；当待展开队列耗尽，仍没有找到目标状态时，才报告**此有限模型中没有计划**。其他规划方法也可能用不同方式证明无解。

缺钥匙案例的结论依赖一个条件：当前没有拿钥匙、借钥匙、绕路或其他能产生相应前置的动作。现实中是否存在这些方法，要先把它们的条件和效果纳入模型，再重新判断。

<details>
<summary>为什么还要记住“已经见过的状态”？</summary>

门打开以后，机器人可能从 A 到 B，再从 B 回 A。若状态中的其他事实都没变，就回到了曾经见过的同一个状态。重复展开不会产生新的可能性。去重还会避免“对已经打开的门再做 open”这样的状态不变操作把搜索拖成无限循环。

</details>

<details>
<summary>先自己说：目标已经在初态成立，正确答案应是几步？</summary>

</details>

## 06 · FSM 管过程，规划器找办法。

*执行逻辑与目标搜索，可以一起用*

[本节网页与交互](../day-03.html#fsm)

**有限状态机 FSM** 用有限个状态和转换规则表达系统行为。你在 UE 中可能见过角色“待机、移动、交互”的状态机。进入哪个状态、收到什么事件再转到哪里，都需要定义。

例如已经拿到一条计划，执行器当前“等待开门反馈”。只有收到成功反馈才进入下一步；收到失败反馈则停止推进、更新状态或请求重规划。**发出了开门请求，不等于收到了开门成功。**

**动手看**

先发出一个动作请求，再分别尝试“成功反馈”和“失败反馈”。留意计划指针什么时候前进，什么时候停在当前步骤。

**交互入口：[给计划执行器发送成功或失败反馈](../day-03.html#day3-fsm)**

*图示说明：这是计划执行器的事件驱动教学状态机。反馈由你点击提供，用于理解接口；它没有读取真实传感器。*

**这些名词的角色不同，可以组成一个系统**

| 名称 | 它是什么 | 本例承担的事情 |
| --- | --- | --- |
| FSM | 表示状态与转换的方式，可用于行为控制 | 等待反馈、继续、停止、恢复 |
| PDDL | 规划问题的描述语言 | 声明初态、目标、谓词和动作规则 |
| 任务规划器 | 根据模型求计划的程序 | 寻找 unlock → open → move → pickup 等序列 |
| TAMP | 结合任务与运动可行性的规划问题与方法体系 | 把离散动作选择与连续姿态／轨迹检查联动起来 |

这不是三种互斥选项。FSM 也可以表示环境状态转换；规划得到的动作序列也可以交给 FSM 执行。有些系统还能把计划编成策略。这里的区别是**当前把哪部分规则交给人写，哪部分交给搜索，怎样接收执行反馈**。

<details>
<summary>先自己说：为什么动作超时后，不能直接把预期效果写成真实状态？</summary>

超时只说明在当前等待范围内没有确认成功。门可能没打开，也可能打开但反馈丢失。应依据后续观察确认状态；不能仅因为计划里写了 opened，就把它当成真实已发生的事实。

</details>

FSM、任务级策略与规划的组合方式，见 [MIT · Programming the Task Level](../day-03.html#source-mit)。

## 07 · “开门、过去、拿起”，还没有告诉身体怎样运动。

*从离散动作，走回连续空间*

[本节网页与交互](../day-03.html#motion)

到这里，符号规划器只知道机器人在某个房间、门的状态、物体属性与声明的能力。真实动作还要选择**底座站在哪里、每个关节转多少、手从哪条路线接近、整段运动会不会碰撞**。

**离散**选择例如“先开门还是先拿物品”；**连续**量例如站位坐标、关节角和随时间变化的运动。把 move 写进计划，只选定了高层动作，不能代替这些具体量。

### 第一件事：门开了，身体宽度是否放得下？

先把机器人简化成俯视图里的圆盘。门洞沿横向的可用区间是 [L,U]，机器人直径 b，每侧留余量 s。圆盘中心必须落在 `[L + b/2 + s, U − b/2 − s]` 里，整个身体和余量才会留在门洞内。

**动手看**

先减小门宽，再移动机器人中心。分开回答：是否存在一个能通过的中心位置？当前选择的中心位置是否合格？展开路径对照，再看为什么起终点合法仍不够。

**交互入口：[圆盘净宽与给定路径检查](../day-03.html#day3-clearance)**

*图示说明：圆盘、门洞与给定路径的受限二维解析检查。允许接触或余量规则在组件内明确；真实机器人形状、门扇运动和接触控制需要另外建模。*

门宽至少为 `b + 2s`，这个中心区间才非空。它给出了当前圆盘模型的尺寸条件；如果改成能够转向的长方形机器人，允许姿态也会影响通过性，就不能把这条固定圆盘结论原样照搬。

### 第二件事：手能不能到达门把？

**逆运动学 IK** 要解决的是：给定末端的目标位置或姿态，寻找符合要求的关节配置。Day 4 会细讲；今天先用两段手臂看懂“有目标位置”和“身体够得着”的区别。

**动手看**

把门把手向上移动，看看什么时候超出可达区域。再切换两种肘部姿态：同一个目标点，为什么可以对应不同关节配置？

**交互入口：[平面两杆手臂的点可达区域](../day-03.html#day3-reach)**

*图示说明：平面两转动关节、固定基座、无关节限位的解析示意，只检查末端点位置。它没有验证末端朝向、连杆碰撞、握住门把后的开门运动或真实执行。*

<details>
<summary>愿意多走一步，再看这个环带的公式</summary>

两杆长度为 L₁、L₂，目标到基座的距离为 r。完全伸直时最远到 L₁+L₂；允许自由折叠时，最近到 |L₁−L₂|。所以末端点的可达条件是 `|L₁−L₂| ≤ r ≤ L₁+L₂`。本图只在这个理想模型里用解析公式求肘上／肘下配置。

可达区域的中心是手臂基座，不是地面原点。基座有高度时，要先用“门把高度减基座高度”计算竖直距离。这和 Day 1 统一坐标系的要求相连。

</details>

### 第三件事：起点和终点都合法，中间能连起来吗？

手在起点不碰墙、在终点也不碰墙，直线过去时仍可能穿墙。**运动规划**需要找到符合所建模约束的整条路径或轨迹。若还关心速度、加速度与动力学，也要将相应条件纳入；一条画在图上的线没有自动提供这些保证。

再把 Day 1 的机械臂构型 q 想起来：路径可以看作一串连续变化的 q；给路径配上时间，就能描述何时处在什么配置。这里先理解“全程要检查”，不要求今天推导轨迹优化。

<details>
<summary>先自己说：IK 求解器一次没有找到解，能断言门把绝对够不到吗？</summary>

不能一概而论。当前解析两杆模型可以按距离边界证明点不可达；一般数值 IK 或运动规划可能因初值、局部极小、采样或时间预算没有找到解。需要区分几何证明、候选被拒绝和搜索尚未找到结果，并报告实际证据。

</details>

IK、轨迹与求解失败的边界见 [MIT · Motion Planning](../day-03.html#source-motion)。圆盘净宽、两杆环带与线段碰撞演示为本教程的解析实例。

## 08 · 高层说“开门”，低层需要带回具体证据。

*Task and Motion Planning · 任务与运动规划*

[本节网页与交互](../day-03.html#tamp)

**TAMP** 把任务层的动作选择，与运动层的连续可行性结合起来。运动失败会影响高层选择；高层改变动作、对象或顺序，又会产生新的运动问题。两部分需要交换信息。

例如一个抓取姿态能拿起杯子，却让杯子无法穿过狭窄区域，后续搬运动作就反过来约束前面的抓取选择。为每一步分别随便找一个姿态，还不一定能拼成同一条完整计划。

**动手看**

先看标准世界；再选缺钥匙、窄门或把手过高，逐步推进检查。留意反馈指出的动作、对象和具体条件。若修改门宽或把手高度，再比较世界版本与重新检查结果。

**交互入口：[任务与运动检查之间的失败反馈](../day-03.html#day3-feedback)**

*图示说明：本图示范任务与运动检查之间的信息往返。它只实现明确列出的符号及解析条件，帮助读懂接口；完整 TAMP 算法还涉及连续参数搜索、动作耦合和执行监测。*

### 一个有用的失败反馈，至少说清五件事

| 反馈内容 | 本例记录 |
| --- | --- |
| 在哪个世界 | world-v1，门 D 的净宽为 0.50 m |
| 哪个动作／对象 | move(r,a,b,d)，通过门 D |
| 哪条条件 | 圆盘机器人直径 0.60 m；此例余量为 0 |
| 什么证据 | 0.50 < 0.60，因此这个固定圆盘无法通过该净宽 |
| 结论范围 | 阻止通过这扇门；不自动否定其他门、其他机器人或改变后的环境 |

同样叫“失败”，可能是很不同的证据。要给上层的是可解释的条件、上下文与范围，不能把一次数值求解失败扩大成“这个对象永远不能用”。

**遇到问题后，下一步应该改什么？**

| 情况 | 可讨论的下一步 | 需要保留的区别 |
| --- | --- | --- |
| 当前状态没有钥匙 | 若已有合法取钥匙动作，就把它纳入计划 | 缺少该动作时，当前模型不会自动发明它 |
| 机器人没有开锁技能 | 重新定义任务／能力配置，或选择已具备的替代动作 | 不能把“没有钥匙”和“不会开锁”混成一个条件 |
| 当前通道不适合该身体尺寸 | 若存在其他路线，可重新选择；否则讨论环境或任务修订 | 扩大门洞改变了世界输入，原世界并未因此被证明可行 |
| 某个运动候选失败 | 换站位、抓取或轨迹，按失败证据重新检查 | 未找到解与证明无解，需要不同表述 |
| 执行结果与预测不同 | 观测新状态、定位原因、重规划或停止 | 不能继续沿用已经过时的状态 |

### 和昨天的 Z3，应该怎样连接？

在这个学习流程中，Z3 可以帮助检查或求解明确编码的几何与逻辑要求；PDDL 描述状态和动作，规划器搜索序列；运动模块处理姿态、碰撞与路径。它们交换结构化输入与结果。

这个分工是我们的系统设计选择，不是说“Z3 天生只能处理几何”或“PDDL 一个布尔量就能替代全部碰撞计算”。规划也可以编码成 SAT／SMT；几何检查也可以把带上下文的结果交回任务层。关键是接口中的每个字段究竟承诺了什么。

<details>
<summary>先自己说：为什么“重新规划”与“把门加宽”不能写成同一类修复？</summary>

重新规划通常是在既定世界、能力和目标下重新选择动作及其参数；把门加宽直接改变环境几何。若允许环境编辑，它也可以被明确定义为一个带成本、约束和验证的动作，但不能在原模型没有该动作时偷偷修改输入并声称原任务已解决。

</details>

TAMP 的离散与连续耦合依据 [Garrett 等人的 TAMP 综述](../day-03.html#source-tamp)与 [MIT 课程](../day-03.html#source-mit)。反馈字段与门杯修订流程为本教程的具体化示例。

### 为什么原 MiniLab 会把“有钥匙 + 会解锁”的锁门当作可用？

这是它的简化规则：若钥匙匹配且声明具备 unlock 能力，就把这条门连接加入可用边。它没有真的调用开锁动作，也没有把输入的 locked 改成 false，更没有检查手臂是否能到达门把。

因此，`rule_feasible` 应读作“这些受限规则通过”。`blocked_state`、`blocked_action`、`blocked_geometry` 是这个检查器的分类，并非所有机器人系统共同规定的状态码。多个问题同时存在时，程序的检查顺序还会影响首先返回哪种原因。
